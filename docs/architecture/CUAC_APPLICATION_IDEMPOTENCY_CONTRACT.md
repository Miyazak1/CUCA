## 1. 接口合同

| 接口 | 幂等要求 |
| --- | --- |
| `POST /api/v1/student/application-sets` | 必填 `Idempotency-Key`，创建申请组 |
| `POST /api/v1/student/application-sets/:applicationSetId/choices` | 必填 `Idempotency-Key`，添加选择；路径中的申请组 ID 是有效输入 |

键是区分大小写的 16 至 128 个 ASCII 字符，只允许字母、数字、下划线和连字符。推荐每次新的用户操作生成随机 UUID。缺失、空值、逗号合并的重复 header 或不合法字符返回 400，不进入命令服务。HTTP 标准头处理可能先规范化首尾空白；服务不自行 trim 或截断键。JSON 正文不能提供幂等键或授权依据。

当前两个接口的首次成功和成功重试均沿用 `200 { data: ... }`，不新增原始请求、receipt 或 hash 字段。每次响应仍有独立的服务端 request ID，不能用 request ID 代替幂等键。

| 情况 | 行为 |
| --- | --- |
| 同账号、同操作、同键、规范化后相同输入 | 返回同一已创建资源的当前 owner-scoped 表示，不重复创建 |
| 同一键改了有效输入 | 409，不覆盖原结果 |
| 同键在不同账号或不同操作中使用 | 分别处理，不共享收据、权限或私有结果 |
| 原资源已删除或 choice 已移除 | 不重建；收据命中但资源不可见时 409；choice 父申请组不存在/不属于当前学生时仍按原归属合同返回 403 |
| 已停用账号、已撤销角色、错误 persona/tenant 或已撤销会话 | 拒绝；旧键不是访问授权 |
| 未提交成功的校验/业务/审计故障 | 事务内收据与业务一起回滚；未消费这个键 |
| COMMIT/HTTP 确认结果不明 | 不自动重试；调用方保留原键和原有效输入，明确重试以取得已完成结果或完成之前未提交的操作 |
| 异常的已提交未完成收据 | 503，需要受控核查；不能抢占、超时删除或换键自动执行 |

这不是逐字缓存旧 HTTP 响应。申请组更名、选择状态变化后，重试可能返回更新后的字段；稳定保证是同一个原资源，不是字节相等。未绑定批次的项目仍按组内 program 去重；已绑定批次的目标按组内 program + intake 去重。不同键的无 program 学校意向仍是不同操作，不能宣称全局语义去重。

冻结补充（2026-08-31）：新添加只允许未锁定、未提交的 draft；已有收据的原键恢复不执行新建分支，因此冻结后仍可取回原 choice。新键或改有效输入不能绕过冻结。SQL 对 owner-scoped 父申请组取行锁并复查锁后状态，事务与双向竞争已真库/HTTP 验证，见 [按项目提交合同](CUAC_APPLICATION_SUBMISSION_BACKEND_CONTRACT.md)。

移除补充（2026-08-31）：新 DELETE 使用固定 choice ID 的软删除标记实现重复确认，不复用本合同的 POST 收据机制，也不要求 Idempotency-Key；空请求体，不能发送 `{}`。每次仍核验身份/归属；重复删除不重复状态事件或成功审计，不能影响后来新建的 choice。已移除 choice 的原添加键仍 409。详见 [草稿移除合同](CUAC_APPLICATION_SUBMISSION_BACKEND_CONTRACT.md)。

## 2. 前端接线约束

批次补充（2026-08-31）：添加选择可传 programIntakeId；省略/null 时规范化对象及 v1 摘要字节不变。仅非空批次选择使用包含批次 ID 的 v2 摘要；keyHash 及账号/操作/键范围不变，同键不能跨版本创建第二份资源，也不能更换或取消批次。批次后来关闭时原键仍只能找回原记录，不代表现在可提交。旧库非空升级和独立构造的历史 v1 收据恢复已纳入真库测试，见 [批次合同](CUAC_APPLICATION_INTAKE_CONTRACT.md)。

版本化编辑补充（2026-08-31）：集合读响应新增 revision。备注/奖学金 PATCH 与整组排序 PUT 使用必填 expectedRevision，不使用创建/添加的 POST 收据；旧版本返回 409。无变化且版本当前时不写审计或推进版本。COMMIT/网络结果不明时先读当前集合，不自动换成新版本覆盖，也不把“当前值相同”当作原请求成功凭证。原 POST 键摘要 v1 不变，恢复收据不推进 revision；实际添加/首次移除会推进。见 [编辑与发布合同](CUAC_APPLICATION_SUBMISSION_BACKEND_CONTRACT.md)。

1. 在用户确认一次新操作时生成键，在第一次发出前保留它；网络超时、刷新后的未决操作恢复或重新登录后的重试沿用原键。
2. 重试必须沿用原有效输入。改变目标申请组、学校、项目、批次、奖学金、备注或其他有效字段属于新意图，不能复用已成功的旧键。
3. 不因 500、超时、连接中断或旧结果已删除而自动换键。避免通过连续生成新键绕过去重。
4. 在同账号恢复未决操作；切换账号不能继续发送前一账号的私有操作。如何安全保存待处理正文、何时清除及是否允许跨页面恢复，需要前端/隐私接线设计，不能直接把学生备注长期放入 localStorage。
5. 确认后的正式提交、支付、退款、文件上传及 Agent 操作不在本合同中，不能假定支持相同协议。

本轮未接前端。后端内部服务保留不带键的显式调用，以供已有内部流程和测试使用；这些调用只有事务原子性，没有请求去重保证。公开的两个 HTTP 写入口不能省略键。带键调用但未配置命令存储的 service 返回 503，不静默降级。

## 3. 存储与事务

`0011_student_application_commands.sql` 新增 `student_application_command_receipts`。唯一约束是 `(user_id, operation, key_hash)`，operation 仅允许两个登记命令。保存 request hash、原 request ID、结果资源 ID、创建与完成时间；不保存完整 DTO、申请名称、学生备注、Cookie、密码或原始键。

输入先经闭合字段解析器规范化，再计算 SHA-256 摘要：原输入保留 v1，仅非空批次 choice 使用 v2。解析器按固定字段顺序输出，统一遗漏/空值、UUID 大小写及原有文本规则。choice 摘要包含路径申请组 ID；忽略的客户端 authority 字段不参与摘要。摘要不是加密或匿名化，低熵输入仍可能被猜测，因此收据是受限内部元数据，不能暴露给 Agent 或公开 API。

生产服务工厂把以下步骤放进同一个 READ COMMITTED 事务、同一连接：

1. 检查当前学生角色、无学校 tenant 和教育记录权限；数据库中对 active 用户及未撤销 student grant 取共享行锁。
2. 用 `INSERT ... ON CONFLICT DO NOTHING` 预留收据。相同 scope/key 的并发插入在唯一约束处等待。
3. 预留成功时执行原申请写入、原成功审计，再记录资源 ID/完成时间，最后一起 COMMIT。
4. 未预留成功时，用独立的后续 SELECT 读取已提交收据，比较请求摘要，再按当前 owner 读取原资源。
5. 成功重试写 `student.application_command.replay` 审计，只有 operation 和 originalRequestId 等关联元数据；不重复原 create/add 成功事件。

等待后的读取必须是另一条语句，不能合成依赖旧快照的 INSERT/SELECT CTE。依据 [PostgreSQL READ COMMITTED 说明](https://www.postgresql.org/docs/16/transaction-iso.html)，`DO NOTHING` 可能受到当前 INSERT 快照尚不可见的并发结果影响，而后续命令取得新的快照。

收据预留从不独立提交；任意业务、审计或收据完成失败均回滚。连接提交错误继续向上抛出并丢弃连接，不自动假定失败，也不自动重复事务。正常重试读取同一持久化收据，不需要内存缓存或 sticky session。

账号/角色在该事务中的数据库锁检查不等于全站身份生命周期已经完成。HTTP session 仍在请求入口解析，RequestContext 当前不携带可在事务中锁定的 session ID；在途 logout/会话到期等更广竞态需独立设计。没有新增数据库 RLS，也没有给 Agent 直接 SQL 权限。

## 4. 生命周期与发布门槛

当前没有收据自动过期或键复用。资源 ID 不设随申请删除的外键，删除申请后保留去重凭据；硬删除账号才随 users 外键级联删除。未来若清理收据，必须先定义保留窗口、墓碑及迟到重试行为，不能简单增加 TTL 后仍声称旧键安全。

上线前仍需：

- 收据、申请数量限额，申请写入及重复读取限流，事务/锁等待时限和数据库容量指标。
- 收据及审计的保留、账号删除、备份/WAL/PITR 义务。没有正文不等于没有隐私责任。
- 业务表与收据同点恢复；异步副本、RDS 故障切换、灾备恢复和多地域运行不能仅凭本地测试承诺不重复。
- v1 规范化规则的兼容策略。不能随意改变默认值/摘要结构导致尚未解决的老请求无法匹配；新增规则需要版本化与迁移评审。
- 发布先迁移数据库，再部署支持收据的后端，再按合同接前端。不要回退到忽略键的旧后端后继续接受未决命令。Drizzle 手写迁移与 snapshot 截至 `0011` 已完成本地核对，迁移互斥与 ledger 前缀/hash 核验也已本地验证；后续按 [迁移基线规范](CUAC_POSTGRES_SCHEMA_BASELINE_CONTRACT.md)，仍需不可变发布工件、RDS 恢复与云端验收。
- Auth session/invitation/challenge、Agent 确认及未来支付各自的结果恢复协议；禁止在通用收据中缓存密码、Cookie、一次性明文 token 或支付敏感信息。
