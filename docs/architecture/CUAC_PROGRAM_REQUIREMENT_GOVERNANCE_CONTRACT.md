# CUAC 项目要求审核与发布合同

日期：2026-08-31。范围：BE-0716 的内部后端审核/发布服务。不是 Ops 页面或公开写 API，不是官方招生数据已经上线。

## 1. 入口与角色

实现：`frontend/src/server/catalog/postgres-requirement-governance.ts`；审核凭证规范：`requirement-review.ts`。没有注册 HTTP 写入口、Agent 工具、CLI 导入器或自动发布任务。前端未修改，仍只使用指定 V3 作为产品参考。

所有方法要求服务端构造的 `selectedSurface=ops`、`purpose=catalog_management`、非游客会话、空 school tenant，以及 `internal_catalog_metadata` 数据类别。它们不接受请求正文授予身份、角色或审批人。内部调用方仍是可信计算边界；构造一个 RequestContext 对象不等于完成真实登录或 MFA。

| 方法 | 允许的当前角色 | 作用 |
| --- | --- | --- |
| getVersion / listVersions | cuac_ops、cuac_admin | 检查单个版本或按版本倒序分页；不返回学生、支付或账号凭据 |
| createDraft | cuac_ops、cuac_admin | 创建不可原位编辑的候选版本 |
| approve | cuac_admin | 由不同于整理人的账号审核，绑定准确内容、范围及时间 |
| publish | cuac_admin | 按期望发布 revision 切换显式指针 |
| withdraw | cuac_ops、cuac_admin | 按期望指针与 revision 紧急撤回 |

每次读取和写入均在数据库内复核 active 账号与当前 role grant，持有对应行锁。学生、学校身份、Agent purpose、错表面、学校 tenant 或缺少数据类别均拒绝；不因为账号“也有管理员角色”而自动切换当前角色。

这不是完整 CUAC 员工授权系统：受控开通/撤权、权限粒度、可信 session/step-up、实际 MFA、Ops 入口审计和速率限制仍须在开放后台写接口前交付。现阶段不新增可调用的 Ops 写端点。

## 2. 版本与人工审核

`0017_requirement_review_governance.sql` 为既有要求版本增加 `prepared_by_user_id` 和 `review_evidence_json`。内容、摘要、版本号、批次和整理人均由创建流程确定；服务不提供原位改正文或重审旧版本的方法，修订必须另建版本。整理人外键 RESTRICT，审核证据引用的账号保留/注销须单独治理。

审核凭证严格包含：版本 ID、批次 ID、文档摘要、整理人、审核人、审核时间、生效时间、复审到期时间、逐来源摘要确认、适用范围确认及公开内容确认。逐来源确认必须覆盖文档中的全部来源，不能只勾选其中一部分。审核人与整理人不能相同；这要求至少两个账号参与，不要求第三个独立发布人。

审核人必须实际核对官方来源、学校/院系/项目/批次/招生对象、年度及修订、例外与补交阶段，并确认文本适合公开，不含私人联系方式、学生资料、凭据或内部批注。服务记录这些人工确认，不自动证明其真实发生，也不会抓取 URL。来源保全、受控采集/校验流程、复核责任和权限审查仍是生产数据准入条件。

`expectedContentSha256` 必须匹配待审版本。所有来源抓取时间不晚于审核时间。`effectiveFrom=null` 表示以数据库审核时间立即生效；明确指定时必须不早于审核时间，`reviewDueAt` 严格晚于生效时间。审核时间使用锁等待后的数据库时钟，不能由客户端回填。审核通过不自动发布，也不表示学生符合资格。

服务生成的审核凭证做规范化摘要，内部 DTO 返回 `approvalSha256` 供发布时确认。凭证与版本、正文摘要、人员和全部时间绑定；仅修改正文并重算 content hash，或延长有效期，不能复用原审核凭证通过读取校验。摘要不是签名，数据库管理员仍可同时改数据与凭证；生产数据库 ACL、可信发布身份及不可变审计保护尚须独立验收。

## 3. 并发与恢复

每个操作使用同一连接和事务：锁定当前账号/角色，再锁学校、项目和具体入学批次；写入者在批次行上串行，读取者持共享锁以一致地读取版本与指针。需要批准/发布时，在版本及指针锁等待后重新检查数据库时钟，防止等待期间已过期。

1. 创建：调用方先生成稳定 UUID 作为 versionId。服务在批次锁内分配递增版本号。相同 UUID、同整理人、同批次及同规范化正文重试，返回原版本当前表示，不再创建或审计；身份/范围/内容不同则冲突。UUID 不是权限。调用失败后保留原 UUID，不自动换新 UUID 重复创建。
2. 审核：draft 只能审核一次。相同正文的两个并发审核也只有一个成功；另一个返回 409。网络或 COMMIT 结果不明时读取原 versionId，检查人员、内容、凭证与时间，不能以客户端超时断言失败或自动重新审核。
3. 发布：必须提交 versionId、expectedContentSha256、expectedApprovalSha256、expectedPublicationRevision。尚无指针时 revision 为 0，其他时候必须是刚读取的正整数。只发布当前已生效、未到复审期、有效目录/批次下的受控审核版本；未来生效版本须等到生效后显式发布，没有自动调度。
4. 同一 active 版本、相同当前 revision 的发布为 no-op。其他切换只能到更高版本号；先前已撤回的同版本不能重新激活，也不能回退到低版本。需要恢复旧内容时，新建版本并重新审核。
5. 撤回：必须同时匹配原 versionId 和 revision，理由使用固定枚举，不收任意备注。实际撤回推进 revision；已经撤回且携带当前 revision 为 no-op，旧 revision 仍冲突。即使目录被停用、正文损坏，也可撤回原指针；不因此读取或信任损坏正文。
6. 每个实际写入与 metadata-only 成功审计在同一事务完成。审计只保存范围 ID、版本/摘要、revision 和枚举理由，不复制正文、来源 URL 或审核确认正文。审计失败全部回滚。读取和 no-op 不增加成功写审计。

创建以稳定 ID 恢复；其余命令主要以状态读取和 CAS 恢复，不提供完整操作收据历史。不要把“现在已是相同状态”当作原请求曾成功的证明，实际归因需查审计。所有版本/revision 为正 int，上限冲突而非溢出或归零。

listVersions 每页 1..50 项，默认 20，按版本倒序、beforeVersion 排除游标本身；只返回摘要元数据，正文由 getVersion 单独读取。它不是跨多次请求固定的数据快照；原位编辑禁止，后续新增版本应从第一页重新检查。

## 4. 对公开接口的影响

游客和登录用户仍读取同一个 11 字段白名单 DTO，固定 `assessmentMode=information_only`。审核人/整理人 ID、审核凭证、权限状态和内部摘要不进入公开响应。Agent 将来仍只允许经 Gateway 获取公开投影，不直接使用本服务。

没有完整新审核依据的旧版本不公开，返回 null；有凭证但绑定错误或损坏的已发布版本返回脱敏 503，不回退旧文本或旧版本。数据库中的 approved 字符串、既有 isVerified、最高版本号或 Agent 的判断都不能代替审核凭证。

## 5. 迁移与部署

本治理阶段为 18 条迁移、9 份快照，最新 0017；旧 0000..0016 的 SQL 字节和 journal 前缀不变。项目后续当前基线见 [结构基线合同](CUAC_POSTGRES_SCHEMA_BASELINE_CONTRACT.md)。本阶段新增两列默认 null，没有自动生成整理人、审核凭证或重审旧记录。旧正文、申请、学生资料及幂等收据保留；旧 approved 行允许保留为 legacy，但不能由服务直接补成已审记录，必须创建新版本并走审核。

发布顺序：先关闭要求读取入口的外部流量，应用迁移，再部署并排空所有旧读取/写入实例，核验没有绕过凭证检查的旧入口，最后恢复只读服务。真实规则只在完成受控来源流程和后台授权后才能发布。旧记录暂不可见是明确安全兼容性变化，不应通过批量伪造确认修复。

回退先停受影响服务并保留新列、凭证和 revision；不能直接恢复 0016 的旧读取逻辑，否则可能重新暴露无新审核依据的旧发布记录。禁止删列、清空凭证、重置版本或改写历史 SQL。阿里云 staging 的混合版本排空、最小权限、TLS、恢复/PITR 与正式发布审批继续单独验收。

## 6. 验收与下一步
