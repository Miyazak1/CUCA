# CUAC 学校申请目标一致性合同

日期：2026-09-01。范围：项目/批次关系约束及学校只读投影。已完成本地实现与验收，最终证据见 [演练记录](CUAC_POSTGRES_REHEARSAL_REPORT.md)；不是正式提交、学校收件授权或生产发布批准。

## 1. 要解决的问题

既有 choice/set/student/school 复合外键保证归属，却不能阻止 school_application.program_id 指向同校另一个项目。仅分别检查两个项目都属于同校不够，也不能只在应用代码中比较后写入。

学校申请必须与它绑定的 choice 精确对应项目和入学批次。每个 choice 仍至多一条 school_application，同校不同项目、同项目不同批次继续独立。申请人/学校/父集合归属约束保持，不新增学校级合并逻辑。

这是平台内部记录的粒度，不等于高校允许同时递交多个项目，也不决定收几次申请费。官方表单、志愿组、第一/第二志愿和顺序限制应作为独立的、按招生周期审核的规则；如需官方递交分组，只建立映射，不覆盖项目明细或把一项结果复制给其他项目。当前 rankOrder 只是学生内部排序，不能直接作为官方志愿序号。正式规则和对接尚未实现，详见 [提交合同](CUAC_APPLICATION_SUBMISSION_BACKEND_CONTRACT.md)。

## 2. 数据库设计

- school_applications 新增 nullable program_intake_id。它是已有 choice 批次标识的受约束副本，不是从 targetIntake 文本猜测的年份/学期，也不是材料快照。
- 两张表分别增加数据库生成的非空 target_key，由 program_id 和 program_intake_id 的 UUID 文本拼成；null 使用空段，分隔符为 `/`。UUID 不含分隔符，因此含 null 的不同目标也不会混同。
- application_choices 上增加 `(id, target_key)` 唯一索引；school_applications 的 `(application_choice_id, target_key)` 通过复合外键引用它。
- target_key 是 GENERATED ALWAYS STORED 列，调用方不能填写或覆盖。它只用于完整性约束，不进入学生/学校 DTO、Agent、审计正文或幂等摘要。
- 外键默认 NULL 语义会跳过含 null 的引用；本设计通过非空生成键约束“缺少项目/批次”与“明确项目/批次”的差异，而不是允许 null 绕过校验。参见 [PostgreSQL 外键](https://www.postgresql.org/docs/16/ddl-constraints.html) 与 [生成列](https://www.postgresql.org/docs/16/ddl-generated-columns.html)。

旧的未绑定意向可以保持 null，但学校记录必须与 choice 同样未绑定。这不允许把意向当作可正式提交的完整申请；正式提交仍须有效项目及批次、同意、材料与费用权益。

学校申请的 program 外键改为 RESTRICT：已有学校记录时，不能通过删除目录项目将目标清空。未形成学校记录的无批次草稿继续保留原 SET NULL 行为；已绑定批次的草稿仍受既有 RESTRICT 保护。停止招生应退役目录对象，不硬删被申请引用的项目。

这保证当前行之间的关系，不是防数据库管理员同时改写所有关联行的不可变历史机制。未来提交仍须保留独立的项目身份、材料版本、授权及事件证据；不能用本生成键冒充签名或提交收据。

## 3. 旧库升级

只追加 0020 迁移，不改历史 SQL。迁移事务先锁定两张申请表，再检查既有 school_application.program_id 与 choice.program_id 是否 IS NOT DISTINCT FROM；任一错配，包括单边 null，立即失败并回滚。不得自动改成 choice 的项目、删记录、合并申请或放弃约束。

检查通过后，新增学校批次列，仅从已经关联的 choice.program_intake_id 复制值。所有原有字段、时间、状态、项目、私有投影和收据保留；未知批次仍未知。该复制只固化当前数据库明确关系，不声称恢复了过去实际递交时的招生批次。真实历史申请须另行核对来源与提交证据。

之后生成两张表的 target_key、先建被引用唯一索引，再建已验证外键。不能以 NOT VALID 长期掩盖旧数据问题。两张表在升级期间暂停写入；表重写、索引、WAL/磁盘和锁等待预算必须在阿里云 staging 按实际数据量演练。

新内部写入必须从同一受控事务中锁定的 choice 复制项目及批次；缺少或错配批次直接拒绝，不让数据库自动猜补。旧写入者必须排空再恢复入口，不能新旧版本混跑。现阶段没有新增正式提交或学校写 HTTP。

回退暂停受影响读写，保留新列、生成键、约束和现有记录；不能恢复允许同校错项目的旧写入方式，也不能删列或改写既有迁移。发现历史错配时，先保留证据并人工确定哪个目标正确，再通过单独批准的修复流程重试升级。

## 4. 读取与权限

学校只读队列/详情新增 programIntakeId，仍只从本校 school_applications 投影读取；不为获取批次去拼接学生全量 choices、资料、备注或 Agent 记忆。原有 membership、tenant 和审计边界不放宽。programId/批次仅表示该条本地记录的目标，不能据 pending_submission 推断高校已接收。

保留现有 HTTP 语义：非学校身份或无有效成员资格为 403；有效老师查询他校或不存在的记录均为 200 `{ data: null }`，两者不能通过正文区分。不能只检查 HTTP 成功码就认为拿到了学校记录。

本轮不新增 API 方法，不改学生草稿命令输入、不改 choice v1/v2 幂等协议、收费单位或前端页面。preflight 仍 preparation_only、canSubmit=false。

## 5. 验收门槛

- 改动前用真库复现同校错项目可写入。
- 同校项目、同项目批次、单边 null、跨学生/学校/父集合错配均拒绝；正确目标和旧未绑定目标可读。
- 直接写入生成键、单边修改任一目标、已有收件后的删除/置空/批次重绑均不能绕过。
- 验证申请写入和 choice 目标变更的双向真实锁竞争及回滚，保证不存在并发错配；不宣称代替提交权限锁。
- 同校独立申请的状态与事件互不影响，学校只读队列/详情返回精确项目及批次，另一学校/学生无权读取。
- 从非空 0019 独立发布包升级，逐项保留旧字段、只复制明确批次；错配旧库失败时 schema、ledger、原数据全部不变，错误脱敏。
- 新 SQL 与 ORM 影子库、生成表达式、外键/索引及快照一致；同摘要独立包通过 Linux 迁移门槛。

最终本地结果：常规后端 416/416、数据库 273/273、数据库与真实网络联合 344/344、独立 Linux 迁移 7/7。数据库与联合入口重叠，不相加计算场景。新增十项业务真库、四项旧库升级、三项真实 HTTP；显式 API 方法仍为 54 个，Student/Auth 写方法仍为 26 个，没有新增写入口。

已封存基线至 0020，共 21 条迁移、12 份快照、46 表；SQL 链与 ORM 影子库一致为 606 列、176 个约束、155 个索引。最终同摘要发布包为 `69d8329afe046785bd42da5a44ea44e0a7c61ffe32a90856d7256b243ce7c1b6`，Linux 停止/回滚/显式重试也使用该包。测试数据均为临时合成数据；临时服务结束，归属标签下无容器、网络或运行镜像残留。

真实同意、材料快照、官方学校递交规则、费用权益、正式提交、生产权限及云端验收仍按 [申请合同](CUAC_APPLICATION_SUBMISSION_BACKEND_CONTRACT.md) 和 [生产计划](CUAC_PRODUCTION_DELIVERY_PLAN_CN.md) 继续。
