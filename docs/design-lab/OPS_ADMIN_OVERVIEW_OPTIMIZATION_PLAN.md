# CUAC 运营管理后台概览页优化方案

版本：2026-08-27  
范围：`design-lab/ops-admin.html#overview` 概览页  
目标文件：`design-lab/completion.js`、`design-lab/completion.css`、必要时 `design-lab/shared-shell.css`

## 1. 结论

当前概览页的后台方向是正确的：它已经具备运营控制台需要的 KPI、待处理事项、系统健康、模块入口、治理信息和风险观察。但页面存在一个核心问题：所有信息几乎以同一种密度出现，导致用户无法快速区分“今天必须处理”“只是状态观察”“可以稍后阅读”的内容。

优化方向不是简单地把所有内容都包进卡片，而是采用混合节奏：

- 顶部摘要保持控制台感，压缩而快速。
- 今日处理使用强卡片，是页面最重要的行动区。
- 系统健康使用小卡片，是安静的状态观察区。
- 管理模块使用中等卡片，是主要导航区。
- 治理、数据归属、风险观察使用轻分区或轻卡片，是辅助阅读区。

这样既能降低文字密度，又不会把后台做成满屏卡片墙。

## 2. 当前问题诊断

### 2.1 信息密度过于均匀

首屏同时展示标题、状态标签、当前重点、6 个 KPI、6 个分区 Tab、今日处理、系统健康。每一块都在强调数字和状态，视觉优先级不够分明。

用户进入概览页时真正需要的第一判断是：

1. 今天有没有高优先级问题？
2. 哪些问题会影响申请闭环？
3. 应该进入哪个模块处理？

现在这些答案都存在，但被太多同权重信息包围。

### 2.2 顶部 KPI 数量偏多

当前 KPI 为：

- 目录学校
- 项目记录
- 学生申请
- 待跟进
- 发送重试
- 审计事件

其中“目录学校、项目记录、学生申请”更像规模背景；“待跟进、发送重试、审计事件”更像需要处理的运营压力。两类信息并排放在首屏顶部，会让用户难以判断哪几个数字最重要。

### 2.3 今日处理不像任务区

今日处理目前是列表式结构。它内容正确，但视觉上更像报表行，不像“现在就去处理”的任务队列。对运营后台而言，这一块应该是最强行动区。

### 2.4 系统健康说明偏显眼

系统健康有价值，但不应该和今日处理争夺主视线。它适合变成小型状态卡片：每张卡一个指标、一句状态、一种轻微风险色。

### 2.5 管理模块入口文字偏长

模块入口现在每行都有较完整说明。说明准确，但扫读成本高。概览页不需要解释每个模块的完整职责，只需要帮助用户快速进入正确模块。

### 2.6 移动端首屏节奏不佳

390px 宽下，6 个 KPI 变成单列，占用过高；底部 Agent 输入条还会覆盖部分内容。移动端应优先露出：标题、当前重点、核心 KPI、今日处理入口，而不是完整统计清单。

### 2.7 评审入口被登录兜底干扰

干净状态下访问 `ops-admin.html#overview` 会先进入登录/Hub 兜底页。作为 design-lab 评审链接，这会干扰设计评估。后续可增加 demo preview 状态或评审说明。

## 3. 优化原则

### 3.1 卡片只用于承载明确对象

适合做卡片：

- 今日任务
- 系统健康单项
- 管理模块入口
- 高风险监控单项

不适合重卡片化：

- 页面标题
- 全局 KPI 条
- Tab 导航
- 数据归属说明
- 上线门禁清单

### 3.2 每个区域只回答一个问题

- 顶部摘要：今天是否紧急？
- 今日处理：先做什么？
- 系统健康：哪里异常？
- 管理模块：去哪里处理？
- 治理信息：上线和数据边界是否安全？

### 3.3 文字从“解释型”改为“决策型”

概览页文案应尽量短，重点说明影响和动作，不展开背景。

示例：

当前：检查已付款但未同步到学校租户的申请记录。  
建议：已付款未发送，影响学校可见。

当前：管理城市指南、公共奖学金和申请时间窗记录，避免把独立内容塞进学校编辑器。  
建议：城市、公共奖学金、时间窗。

### 3.4 视觉强度分层

强视觉：

- 今日处理卡片
- 高优先级状态
- 主行动按钮

中视觉：

- 管理模块卡片
- 系统健康卡片

弱视觉：

- 顶部规模 KPI
- 数据归属
- 上线门禁
- 审计摘要

## 4. 推荐页面结构

### 4.1 顶部：压缩控制台头部

保留：

- 返回 CUAC
- 内部运营
- 运营管理后台
- 一句说明
- 状态标签
- 当前重点

调整：

- 当前重点从右侧读数改为更清晰的“今日压力条”。
- KPI 从 6 个压缩到 4 个核心运营压力指标。

建议顶部 KPI：

1. 高优先级队列
2. 待跟进学生
3. 发送重试
4. 待审批 / 审计异常

目录学校、项目记录、学生申请这类规模数据移入模块卡片。

### 4.2 今日处理：2x2 强任务卡片

这是概览页的主操作区。

卡片结构：

- 左上：数量
- 标题：任务名
- 一句影响说明
- 底部：主动作

推荐任务卡：

1. 支付后发送
   - 数字：2
   - 说明：已付款未发送，影响学校可见。
   - 动作：处理

2. 学生待跟进
   - 数字：2
   - 说明：资料、联系或重发通知待推进。
   - 动作：查看

3. 学校数据复核
   - 数字：1
   - 说明：截止日期、来源或字段映射需确认。
   - 动作：复核

4. 账号待审批
   - 数字：1
   - 说明：学校老师、运营角色或 Agent 权限待审。
   - 动作：审批

布局：

- 桌面：4 卡一行，或 2x2，取决于可用宽度。
- 中屏：2x2。
- 移动：单列，但应出现在 KPI 后立即可见。

### 4.3 系统健康：安静的小卡片

系统健康不要和今日处理同等强度。建议放在今日处理右侧或下方，用 2x2 小卡片。

卡片结构：

- 标签
- 大数字
- 状态说明
- 可选轻微风险色

指标：

- 目录质量 89%：1 所学校需复核
- 支付通过 67%：2 个学生已支付
- 租户权限 4：1 个账号待审批
- Agent 就绪 78：申请辅助免费开放

视觉要求：

- 小卡片背景可用浅色，不需要厚边框。
- 数字是主角，说明只保留一行。
- 风险色只用于异常，不要每张卡都彩色。

### 4.4 管理模块：中等导航卡片

当前模块入口文字偏长，建议改成卡片网格。

卡片结构：

- 标题
- 核心数量
- 2 到 4 个短标签
- 右上角箭头或底部弱按钮

示例：

学校数据  
3 所学校 · 4 个项目  
学校档案 / 项目 / 奖学金 / 来源

内容数据  
23 条内容记录  
城市 / 公共奖学金 / 时间窗

学生申请  
3 人 · 2 待跟进  
资料 / 支付 / 发送 / 跟进

账号权限  
4 个账号 · 1 待审批  
角色 / 租户 / Agent / 审计

队列与审计  
3 个高优先级 · 3 条审计  
重试 / 支持 / 拒绝 / 导出

布局：

- 桌面：5 张卡可使用 `repeat(5, minmax(0, 1fr))`，如果太窄则 3+2。
- 中屏：2 列。
- 移动：单列或横向滚动卡片；优先单列，避免横向操作成本。

### 4.5 管理层摘要：保留，但降权

管理层摘要目前较稳定，可以保留图表结构，但应放在管理模块之后，避免过早进入分析视角。

建议顺序：

1. 顶部摘要
2. 今日处理 + 系统健康
3. 管理模块
4. 管理层摘要
5. 治理与风险

原因：概览页优先服务一线运营，不是先服务汇报阅读。

### 4.6 治理与风险：轻分区混合卡片

底部三块可以这样处理：

- 上线前检查：保留 checklist，弱卡片。
- 数据归属：保留文本说明 + token list，弱卡片。
- 高风险监控：可改成小风险卡片，强调异常数量和处理入口。

这一块不需要大面积卡片，否则会让页面尾部变重。

### 4.7 分析汇总升级：学生洞察与学校运营

当前的“管理层摘要”不能只做成少量概览图表。它需要承担两个核心问题：

1. 学生现在想要什么，以及他们卡在哪里。
2. 学校供给、学校数据和运营动作是否能接住这些需求。

因此分析汇总建议升级为“学生洞察 + 学校运营汇总”的组合区块，而不是单纯的状态统计。

学生洞察应覆盖：

- 国家/地区来源：保留国家需求，但需要更细，至少能看到来源国家 Top、目标国家/城市偏好、不同来源学生的申请阶段差异。
- 城市选择：统计学生收藏、加入 checklist、已提交或已发送的城市分布，区分“感兴趣”和“真正进入申请”的城市。
- 专业选择：统计专业方向、学位层级、授课语言偏好，以及专业选择与 HSK、CSCA、奖学金需求之间的关系。
- 学校与项目选择：统计只收藏、已加入 checklist、已开始申请、已发送学校的分布，识别只看不申请、单校集中、多校分散等行为。
- 奖学金申请：统计必须奖学金、偏好奖学金、可自费、不确定四类学生，以及奖学金项目选择、材料准备和提交进度。
- 关注点分析：汇总学生更关心城市、学校排名、学费、奖学金、英文授课、专业匹配、录取把握、毕业就业等因素。
- 经济与资助：汇总预算范围、奖学金依赖度、资金证明准备情况、可接受自费比例和低成本偏好。

学生准备情况应覆盖：

- 个人资料：基本信息、联系方式、护照、教育经历、紧急联系人等完成度。
- 申请材料：成绩单、毕业/在读证明、推荐信、学习计划、护照扫描件、翻译公证等准备状态。
- HSK 准备：当前等级、目标等级、是否已报名、考试日期、成绩是否可用。
- CSCA 准备：是否需要、是否已开始准备、报名/考试/成绩状态。
- 其他考试：IELTS、TOEFL、校内笔试、面试准备等状态。
- 申请阶段：仅加入 checklist、开始填写、已提交、已支付、待发送、已发送、发送失败、学校已查看、学校已联系。
- 支付情况：未支付、支付中、已支付待发送、已退款、支付异常。

学校运营汇总应覆盖：

- 学校与项目供给：学校数量、项目数量、奖学金数量、英文授课项目、需要 HSK/CSCA 的项目占比。
- 数据质量：学校来源复核、项目字段缺失、奖学金规则缺失、申请截止时间缺失、CSCA/HSK 规则缺失。
- 学校响应：已发送学校、未查看学校、超过 SLA 未响应学校、需运营跟进学校。
- 供需缺口：学生热门城市/专业/奖学金需求与现有学校项目供给之间的差距。
- 权限与租户：学校老师账号、租户绑定、待审批权限、Agent 权限、审计导出。

这个区块的视觉处理建议：

- 不再使用大段说明文字，改成 3 个分析卡组：学生需求、学生准备、学校供给。
- 每组顶部给一个判断句，例如“奖学金依赖学生占比较高，需优先补齐低成本项目”。
- 图表只用于表达分布和趋势，不替代运营结论。
- 缺失数据必须显示为“待确认”，不能从统计中静默消失。

### 4.8 需要新增的学生资料字段

如果当前个人信息里没有经济情况、考试准备和材料准备字段，需要补采。建议字段先保持运营可用，不要过早复杂化。

经济与资助字段：

- `budgetRange`：预算范围，例如 `<3000_usd`、`3000_8000_usd`、`8000_15000_usd`、`15000_plus_usd`、`unknown`。
- `scholarshipNeed`：奖学金需求，例如 `required`、`preferred`、`optional`、`not_needed`、`unknown`。
- `selfFundingTolerance`：自费接受度，例如 `full_scholarship_only`、`partial_self_funded`、`fully_self_funded_ok`、`unknown`。
- `financialProofStatus`：资金证明状态，例如 `not_started`、`preparing`、`ready`、`not_required_yet`、`unknown`。
- `fundingSource`：资金来源，例如 `family`、`scholarship`、`government`、`employer`、`loan`、`mixed`、`other`、`unknown`。
- `lowCostPreference`：低成本项目偏好，例如 `required`、`preferred`、`neutral`、`unknown`。

考试与语言字段：

- `hskStatus`：未开始、准备中、已报名、已考试、成绩可用、不适用。
- `hskCurrentLevel` / `hskTargetLevel`：当前等级与目标等级。
- `cscaStatus`：未确认、需要但未开始、准备中、已报名、已考试、成绩可用、不适用。
- `englishTestStatus`：IELTS/TOEFL 等英文考试状态。
- `otherExamStatus`：校内笔试、面试或其他考试状态。
- `interviewReadiness`：面试准备状态。

个人资料与材料字段：

- `profileCompletionStatus`：个人资料完成度。
- `contactInfoStatus`：联系方式状态。
- `passportStatus`：护照信息/扫描件状态。
- `educationHistoryStatus`：教育经历状态。
- `transcriptStatus`：成绩单状态。
- `degreeProofStatus`：毕业/在读证明状态。
- `recommendationStatus`：推荐信状态。
- `studyPlanStatus`：学习计划状态。
- `translationNotaryStatus`：翻译公证状态。
- `documentChecklistCompletion`：材料清单整体完成度。

选择与申请字段：

- `studyLevel`：本科、硕士、博士、语言项目、预科等。
- `teachingLanguagePreference`：中文授课、英文授课、中英均可、不确定。
- `choiceStage`：浏览、收藏、加入 checklist、准备申请、已决定。
- `applicationSubmissionStage`：未开始、填写中、已提交、需补材料、已支付、待发送、已发送、发送失败。
- `schoolSendStatus`：未发送、排队中、已发送、失败待重试、学校已查看、学校已联系。

文案注意：

- 面向学生端的字段应使用温和表达，例如“预算范围”“奖学金需求”“资金证明准备情况”。
- 后台可以据此计算运营风险，但学生端不应出现“支付能力风险”这类压迫性措辞。

### 4.9 后续前端落地建议

概览页后续可以把当前管理层摘要拆成以下组件：

- `renderOpsStudentDemandInsights`：国家、城市、专业、学校、奖学金、经济偏好。
- `renderOpsStudentReadinessInsights`：资料、材料、HSK、CSCA、考试、支付、发送进度。
- `renderOpsSchoolOperationsInsights`：学校供给、数据质量、学校响应、供需缺口。
- `buildOpsStudentInsightStats`：从学生、申请、checklist、支付和材料数据生成统计。
- `buildOpsSchoolInsightStats`：从学校、项目、奖学金、租户和审计数据生成统计。

第一版可以先在 mock 数据中补字段，再用真实数据接口替换。验收标准是：运营人员打开概览页后，能同时回答“学生在选什么、学生准备到哪了、学校供给是否匹配、下一步该跟进谁”。

## 5. 建议文案改写

### 5.1 页面说明

当前：

管理目录数据、学生申请、支付发送、租户健康和 Agent 审计。这里是内部运营工作台。

建议：

处理申请闭环、目录质量、账号权限和 Agent 审计。高风险动作必须留痕。

### 5.2 当前重点

当前：

3 个高优先级队列  
2 个发送重试 · 2 个学生待跟进 · 1 所学校需来源复核

建议：

今日优先：3 个高风险事项  
发送重试 2 · 学生跟进 2 · 来源复核 1

### 5.3 今日处理标题

当前：

先处理会影响申请闭环的事项

建议：

先处理会阻塞申请闭环的事项

### 5.4 模块入口短文案

学校数据：

学校档案、项目、奖学金、申请要求和来源。

内容数据：

城市指南、公共奖学金和申请时间窗。

学生申请：

学生资料、支付、学校发送和跟进状态。

账号权限：

统一账号、学校老师邀请、运营角色和 Agent 权限。

队列与审计：

支付发送、失败重试、支持查询和策略审计。

## 6. 组件落地建议

### 6.1 新增或调整组件

在 `completion.js` 中建议拆出：

- `renderOpsOverviewHero(stats, state)`
- `renderOpsOverviewCoreMetrics(stats)`
- `renderOpsTodayTaskCards(stats, accessRows)`

这样概览页结构会比当前 `renderOpsPage()` 中直接拼大段 HTML 更容易维护。

### 6.3 卡片视觉规范

任务卡：

- 背景：白色或极浅色
- 边框：`rgb(16 39 43 / 0.10)`
- 圆角：8px 以内
- 数字：24-30px
- 标题：16-18px
- 文案：12-13px
- 主按钮：小号按钮，固定位置

健康卡：

- 背景更轻，不要强阴影
- 数字 22-26px
- 单行说明
- 异常状态使用轻红/黄，不要整卡大面积警告色

模块卡：

- 标题 16-18px
- 数量 12-13px
- 标签 11-12px
- 整卡可点击或右上角箭头按钮

### 6.4 Agent 输入条处理

当前固定 Agent 输入条会遮挡概览内容。建议至少做一项：

1. 在 ops 概览默认折叠成浮动 Agent 按钮。
2. 给 `.completion-shell` 或 `body[data-agent-mode="ops"]` 增加足够底部安全距离。
3. 当滚动未到操作区底部时，让 composer 使用较小高度的 compact 模式。

推荐优先级：默认折叠成浮动按钮。后台页面的首要任务是操作和审计，Agent 应作为辅助入口存在。

## 7. 响应式方案

### 桌面宽屏

结构：

- 顶部 hero：左标题，右当前重点。
- 核心 KPI：4 个一行。
- 主区：今日处理 2/3 宽，系统健康 1/3 宽。
- 模块卡：5 卡一行或 3+2。
- 摘要图表：3 卡一行。
- 治理风险：3 列。

### 平板 / 中屏

结构：

- Hero 单列。
- KPI 2x2。
- 今日处理 2x2。
- 系统健康 2x2。
- 模块卡 2 列。
- 治理风险 1-2 列。

### 手机

结构：

- Hero 压缩，不展示过多状态 pill。
- KPI 2x2，不允许 6 个单列长清单。
- 今日处理单列，紧跟 KPI。
- Tab 导航可以 2 列，但高度需要控制。
- Agent 默认折叠或避让底部。

手机首屏目标：

用户应在首屏看到：

- 运营管理后台
- 今日优先事项数量
- 至少 2 个关键 KPI
- 今日处理区的开头

## 8. 推荐改造顺序

### 第一步：低风险结构优化

- 顶部 KPI 从 6 个改为 4 个核心指标。
- 今日处理改成任务卡片。
- 系统健康改成小卡片。
- 管理模块改成模块卡片。

### 第二步：移动端节奏优化

- KPI 在移动端保持 2x2。
- Agent 输入条默认折叠或增加底部避让。
- 检查 390px 和 768px 宽度下无横向溢出、无遮挡。

### 第三步：文案压缩

- 所有概览页模块说明压缩到一行。
- 模块入口用标签替代长句。
- 风险和治理区只保留关键判断。

### 第四步：评审入口优化

- 增加 demo 运营态入口，避免 `ops-admin.html#overview` 在干净状态先进入登录页。
- 或在 design-lab README 中明确评审前需要进入 CUAC Ops demo 状态。

## 9. 验收标准

### 桌面端

- 首屏能清楚看到标题、今日优先、核心 KPI、分区导航、今日处理开头。
- 今日处理是最强行动区。
- 系统健康不抢今日处理主视线。
- 管理模块可以在 5 秒内扫清每个模块职责。
- Agent 输入条不遮挡按钮和卡片内容。

### 移动端

- 无横向溢出。
- KPI 不变成 6 个单列长清单。
- 今日处理在首屏或首屏后很短距离出现。
- Agent 输入条不覆盖 KPI、Tab 或任务按钮。
- 所有按钮文字不换行到难读状态。

### 信息节奏

- 每个区域的视觉强度不同。
- 卡片数量可控，不形成卡片墙。
- 概览页文字总量下降，行动入口增加。
- 运营用户能快速判断“今天先做什么”。

## 10. 最终建议

采用“控制台头部 + 任务卡片 + 健康小卡 + 模块导航卡 + 轻治理区”的混合方案。

这比纯卡片布局更适合 CUAC 运营后台：既能降低文字密度，又能保留内部工具需要的扫描效率和审计严肃感。页面节奏应从“紧急处理”逐步过渡到“状态观察”，再到“模块导航”和“治理复盘”，而不是让所有信息在首屏同时发声。
